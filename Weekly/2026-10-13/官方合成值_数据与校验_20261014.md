# 官方合成值 数据与校验 2026-10-14

AEMO 三段官方预测拼成一条可直接调用的因果序列,覆盖 2026-08-11 至 2026-10-09 共 60 天,跨度 5 分钟至 183.0 小时。

这一段只讲官方那一侧:是什么、有多大、缺在哪、有多旧、误差多少。与模型的对照在另一份。

## 1 跨度轴

`L_min = [5:5:55, 60:30:10980]`,376 列。唯一权威是 `Predicitor/Shared/official_lead_axis.m`,图集与出图都从那里取。

| 列 | 跨度 | 档距 | 来源 |
|---|---|---|---|
| 1 至 11 | 5 到 55 分钟 | 5 分钟 | P5MIN |
| 12 至 376 | 60 分钟到 183.0 小时 | 30 分钟 | PREDISPATCH,到各自 horizon 之后换 PD7DAY |

**前 11 列不是 12 列。** 一个 P5MIN run 写 12 行,偏移 0 到 55 分钟。偏移 0 描述的是刚结束那个区间,在原点是已知的,不是预测,所以不占列。5 分钟档只能给 11 列,第 12 列(60 分钟)起归 PREDISPATCH。实测每个 run 的最大 lead 恒为 0.9 小时,即 55 分钟,确认这条边界。

**第 60 分钟这一列有一条接缝。** 它不是 P5MIN 给的,是 PREDISPATCH 给的。

## 2 三段索引的实测规模

| 产品 | run 数 | 列数 | 最大 lead | 行数 | 每天 run 数 |
|---|---|---|---|---|---|
| P5MIN | 17,281 | 12 | 0.9 小时 | 207,372 | 288 |
| PREDISPATCH | 2,880 | 79 | 15.5 至 39.0 小时 | 159,840 | 48 |
| PD7DAY | 180 | 367 | 164.5 至 183.0 小时 | 63,240 | 3 |

索引窗口 2026-08-11 00:00 到 2026-10-10 00:00,NEM 时间。

**查表是闭式的。** 三份文件都满足 `target_datetime = effective_time + 档距 × (period_id − 1)`,所以列号 `col = (T − effective_time)/档距 + 1`,边界就是 `0 <= T − effective_time <= leadmax`。不做搜索、不做插值、不就近取整。

**时间戳的口径是量出来的,不是假设的。** 三段产品的行时间戳都是所描述区间的**结束**时刻,与主价格序列的 SETTLEMENTDATE 同口径。判据是把每个 run 的第 j 行拿去与实际价的第 l 个样本比,P5MIN 的 12 个偏移上误差矩阵的对角线 `j = l` 全胜、`l = j + 5` 全负(行 0 对 0 是 16.11 对 19.24,行 50 对 50 是 31.20 对 32.09,11 比 0)。证据在 `Weekly/2026-10-13/predictor/runs/probe_p5min_phase.log`。

## 4 数据年龄

年龄定义为 `原点 − 供给该值的 run 的 effective_time`,单位分钟。**不是那一行相对 run 的跨度**,两者差一个 lead,写错会让 24 小时的格子看起来像用了一个 24 小时前的 run。

| 来源 | 最小 | 中位 | 最大 |
|---|---|---|---|
| P5MIN | 0 | 0 | 0 |
| PREDISPATCH | 0 | 12.5 分钟 | 25 分钟 |
| PD7DAY | 0 | 3.92 小时 | 13.42 小时 |

按跨度看:

| 跨度 | 最小 | 中位 | 最大 |
|---|---|---|---|
| 0.1 h | 0 | 0 | 0 |
| 0.9 h | 0 | 0 | 0 |
| 1.0 h | 0 | 0.21 h | 0.42 h |
| 4.0 h | 0 | 0.21 h | 0.42 h |
| 10.0 h | 0 | 0.21 h | 0.42 h |
| 24.0 h | 0 | 0.33 h | 13.42 h |
| 48.0 h | 0 | 3.92 h | 13.42 h |
| 96.0 h | 0 | 3.92 h | 13.42 h |
| 183.0 h | 0 | 0 | 0 |

**13.42 小时这个上界是 PD7DAY 自己的发布节奏决定的。** 发布在 07:30、13:00、18:00,隔夜那一段是 13.5 小时。所以长期那一侧的数据最多能旧 13.5 小时,做不到更少。这一条是官方数据源的硬边界,不是抓取取舍。

**24 小时那一列出现 13.42 小时的最大值**,说明有一部分 24 小时跨度的格子已经掉到 PD7DAY 了,因为 PREDISPATCH 在那个原点的 horizon 不够。换来源与变旧是同一件事的两面。

**check 1 走的是完全独立的路径。** 它另外读一遍 P5MIN 原始 CSV,用两张时间戳拼成字符串键塞进 `containers.Map`,不经过 `official_composite_load` 的列号算术。

**容差的两个理由。** 立方存 single,所以 check 2 与 check 5 比的是单精度舍入不是精确相等;在 23200 $/MWh 上一个 single ULP 是 0.002,实测最大偏差 9.71e-04。check 5 的 CSV 是双精度写出的,所以它比立方的偏差正是这个舍入。

**三处失败是判据自己写错,不是数据错**,记在这里免得再犯:

1. 拿单精度当双精度比,容差给 1e-6。
2. 把 PD7DAY 的发布间隔写成 11.5 小时,真实隔夜间隔是 13.5 小时。
3. check 5 的日索引从槽位推,槽位在午夜折叠,所以推不出日,跨午夜的格子读到前一天去了。

## 9 工程坑

**一、归约返回向量,`fprintf` 就按元素循环格式。** `sum(X)` 对三维数组只归约第一维,所以 `sum(sum(X))` 仍然返回长度 60 的向量,`fprintf` 把格式跑了 60 遍。`mean(A, 'omitnan')` 不带维度同理,沿第一个非单例维求。这个错本轮犯了两次。做法:三维及以上一律 `sum(X, 'all')`,`fprintf` 之前先 `assert(isscalar(...))`。

**二、重跑长任务不能沿用同一个日志名。** 上一轮的进程仍握着日志句柄时,`Remove-Item` 带 `-ErrorAction SilentlyContinue` 与新一轮的 `>` 重定向**都会静默失败**,读到的一直是上一轮的输出,白白多跑一轮。做法:日志名当参数传,每轮一个新名字。同族的已知坑仍然有效:判"跑完了"看产物,不看日志内容。
